## 1. The publish tools

A **local** Cowork session exposes:

| Tool | Use |
|---|---|
| `mcp__cowork__create_artifact` | first publication |
| `mcp__cowork__update_artifact` | update an existing artifact |

These are **not** `mcp__remote-devices__create_artifact` / `update_artifact`. The
`remote-devices` pair is the cloud persistence path: it never transports the allowlist and
overwrites a working artifact with a broken one. Never use it for this route.

### `mcp__cowork__update_artifact` — parameter schema (verbatim)

```json
{
  "type": "object",
  "properties": {
    "id":             { "type": "string", "description": "Kebab-case slug of the existing artifact to update." },
    "html_path":      { "type": "string", "description": "Path to a file you've already written containing the complete self-contained HTML document. Relative paths resolve against your scratch directory." },
    "update_summary": { "type": "string", "description": "Short description of what this update changes — shown to the user in the approval prompt." },
    "description":    { "type": "string", "description": "Replace the artifact's summary. Omit to keep the existing description." },
    "mcp_tools":      { "type": "array", "items": { "type": "string" },
                        "description": "Replace the fully-qualified MCP tool names (mcp__<server>__<tool>) used in this artifact — only list tools you actually called this session and whose output shape you verified. Omit to keep the existing tool list." }
  },
  "required": ["id", "html_path", "update_summary"]
}
```

### `mcp__cowork__create_artifact` — parameter schema (verbatim)

```json
{
  "type": "object",
  "properties": {
    "id":          { "type": "string", "description": "Kebab-case slug (lowercase letters, digits, hyphens, underscores)." },
    "html_path":   { "type": "string" },
    "description": { "type": "string" },
    "mcp_tools":   { "type": "array", "items": { "type": "string" },
                     "description": "Fully-qualified MCP tool names (mcp__<server>__<tool>) your HTML will call via window.cowork.callMcpTool()." }
  },
  "required": ["id", "html_path"]
}
```

### The allowlist parameter is `mcp_tools` — snake_case

An array of strings, each a full `mcp__<server>__<tool>` id.

**`mcp_tools` (input) and `mcpTools` (output) are different things.** `mcpTools` is a field
of the `cowork-artifact-meta` block, **regenerated by the platform after publication**. It
is a receipt, not a control. Editing it in the HTML grants nothing — which is what PR #59
proved by moving it around with no effect.

There is **no `mcpServerNames` input**. The platform derives it from the server prefixes in
`mcp_tools` and writes it into the meta block. Pass `mcp_tools` only.

### The call that actually worked

```json
{
  "tool": "mcp__cowork__update_artifact",
  "arguments": {
    "id": "edifice-front",
    "html_path": "…/outputs/edifice-front-unblocked.html",
    "update_summary": "Déblocage : allowlist aux deux formes + shim résolveur.",
    "mcp_tools": [
      "mcp__hal-mcp__list_edifice_missions",
      "mcp__hal-mcp__get_mission_context",
      "mcp__hal-mcp__get_mission_photo",
      "mcp__7898d523-5bb3-4502-b704-16db78ae0a8c__list_edifice_missions",
      "mcp__7898d523-5bb3-4502-b704-16db78ae0a8c__get_mission_context",
      "mcp__7898d523-5bb3-4502-b704-16db78ae0a8c__get_mission_photo"
    ]
  }
}
```

**Every republication must pass the full list again.** `mcp_tools` replaces the stored list;
the declaration does not live in the HTML, so it cannot be recovered from the file.

**Call a hal tool in-session before publishing.** The schema says "only list tools you
actually called this session" — that is the platform requirement behind step 3 of the skill
route, not a superstition.

## 2. Reading the connector registry

The tool is **`mcp__mcp-registry__list_connectors`** (parameter: `keywords: string[]`).
It is **not** named `ListConnectors`.

`hal-mcp` entry, verbatim:

```json
{
  "name": "hal-mcp",
  "description": "",
  "url": "https://zgkvbjqlvebttbnkklpo.supabase.co/functions/v1/hal-mcp",
  "directoryUuid": "7898d523-5bb3-4502-b704-16db78ae0a8c",
  "connected": true
}
```

The returned fields are **`directoryUuid`** and **`connected`**. There is no
`installedServerId`, no `enabledInChat`, no `installState` — the skill's step 2 was written
against field names that do not exist.

**`hal-mcp` is an account-level connector** (claude.ai Settings → Connectors), not merely a
plugin-scoped MCP server: it appears in the registry with a `directoryUuid`, a URL and
`connected: true`. This settles the open TODO in the skill's step 5 — no separate
account-level installation is needed, it is already one.

## 3. The server is addressable under two names, and they are not interchangeable per context

The same connector answers to:

- its **short name** → `mcp__hal-mcp__<tool>`
- its **directory UUID** → `mcp__7898d523-…__<tool>`

Observed on 2026-07-30, in one and the same local session:

| Context | Form actually used |
|---|---|
| The chat session's own tool names | **UUID** |
| The published artifact's runtime | **short name** |

The artifact's allowlist error named `mcp__hal-mcp__list_edifice_missions` while the session
saw only `mcp__7898d523-…__…`. Two days earlier (2026-07-28) it was the exact opposite.

**Consequences, both mandatory:**

1. Declare **both forms** in `mcp_tools` (6 ids for 3 tools). The allowlist is a permission,
   not a routing table — listing a name that is never used costs nothing.
2. **Resolve dynamically in the bundle**: try the candidate prefixes, keep the one that
   answers, memoize it. Never derive the artifact's runtime name from the session's own tool
   names, and never freeze a single form.

## 4. Two independent photo failures, not one

`get_mission_photo` fails in two unrelated ways. Issue hal#89 §5 attributes both to the
bridge; the measurements below refute that.

Measured from a **chat** session (no artifact bridge involved), photo
`3d7700c2-1760-45b8-805b-852170c0b8c0` of mission "Suivi des travaux" (36 Rue Bayen):

| # | `max_width` | Result |
|---|---|---|
| 1 | 320 | ✅ valid image, normal latency |
| 2 | 1200 | ❌ `tool "get_mission_photo" timed out after 180s` |
| 3 | 320 | ❌ "The connector's server isn't responding" — right after the 1200 call |
| 4 | 320 | ✅ valid image — the instance recovered |

*Instrument limit: the chat renders the image block, so exact millisecond timings and base64
sizes were not readable. Success, failure and timeouts were.*

**Failure A — transport (bridge).** The Electron bridge's result validator accepts text/JSON
and rejects image content blocks. Full error text, unedited:

```
Erreur hal-mcp.
Une erreur inattendue est survenue côté serveur.
Error: Error invoking remote method '$eipc_message$_699a1464-945b-4143-a09c-275519ade04d_$_claude.coworkArtifact_$_CoworkArtifactBridge_$_callMcpTool': Error: Result from method "callMcpTool" in interface "CoworkArtifactBridge" failed to pass validation
```

This affects the small widths — the ones that *do* return. Fixed by returning the base64 as
JSON text (hal#89).

**Failure B — server-side resize.** At ~1200 px the call does not return within 180 s **in
chat, with no bridge in the path**, and leaves the isolate unresponsive to the next call.
Suspects: `magick-wasm` cost/memory, Edge Function CPU/memory limits, cold start (14.6 MB
wasm fetched from CDN per isolate).

**Failure B survives the hal#89 fix.** Changing the transport does not change the resize.
Since `max_width` defaults to **1200**, a JSON-mode call that omits the parameter still hits
failure B. Any consumer must pass an explicit small width until B is fixed.
